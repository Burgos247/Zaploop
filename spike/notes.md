# Spike notes — 2026-05-12

Closes pre-bootstrap risk-down for Zaploop. NWC was mocked against the
documented contract; Wapupay was mapped from its real OpenAPI spec
(`docs/wapupay-openapi.json`, fetched from `https://wapu.shiafu.com/openapi.en.json`).

## What changed in the design

The original plan assumed a single rail where sats from the subscriber
optionally pass through Wapupay for ARS off-ramp. **Wapupay does not work
that way.** Its internal balance is USDT (displayed in ARS), so any sat
that enters Wapu stops being a sat at the moment of deposit. There is no
"keep as sats" mode inside Wapu.

NWC was mocked (see `billing-cycle.mjs`); Wapupay was mapped from its real
OpenAPI spec at `docs/wapupay-openapi.json` (fetched from
`https://wapu.shiafu.com/openapi.en.json`, v0.21.0).

This forces a **two-rail** architecture, confirmed with the user:

- **Self rail** — invoice generated by the merchant's own NWC connection
  (`make_invoice`). Sats land directly in the merchant's wallet. No Wapu,
  no payout option, custody-less. La Crypta cowork case.

- **Wapupay rail** — invoice generated by `POST /wallet/deposit_lightning`
  on the merchant's Wapu account. Sats become USDT in their Wapu balance
  (visible as ARS). Optional: a `payout_pct` per merchant triggers a
  `POST /transactions/create` with `type=fiat_transfer` to the merchant's
  CBU alias after each successful charge. Café/feria vendor case.

Rail is a property of the merchant (or per plan, if we want flexibility).

## Wapupay API — what we'll actually call

Auth: merchant logs into Wapu in their browser, enables API, generates a
token (`POST /users/api-token`, returned once). They paste it into Zaploop.

Per charge:

1. `POST /wallet/deposit_lightning {amount: <sat>}` → invoice + `transaction_id`.
2. Subscriber's NWC pays the invoice (we own this side).
3. Poll `GET /transactions/{id}` until `status: Completed`. **There are no
   webhooks** (zero mentions of `webhook` or `notification` in the spec).
4. If `payout_pct > 0`: read `GET /exchange_rates` for USDT/ARS, compute
   ARS amount = `usdt_received * rate * pct/100`, then `POST /transactions/create
   {type: fiat_transfer, payment_amount: <ars>, currency_taken: USDT, alias,
   receiver_name}`. The created tx is `Pending` until Wapu settles the bank
   transfer — poll that too.

Servers: `be-stage.wapu.app` is the documented staging environment. Use it
for the demo unless real-money flow is needed.

## NWC — confirmed surface

From `@getalby/sdk` README and OpenAPI'd NIP-47 spec:

```js
import { NWCClient } from "@getalby/sdk/nwc";
const nwc = new NWCClient({ nostrWalletConnectUrl: uri });
const info = await nwc.getInfo();            // verify granted methods
await nwc.makeInvoice({ amount, description });
await nwc.payInvoice({ invoice });
```

Errors per NIP-47 use codes: `INSUFFICIENT_BALANCE`, `QUOTA_EXCEEDED`,
`UNAUTHORIZED`, `NOT_IMPLEMENTED`, `INTERNAL`, `OTHER`. The spike treats
each of these as a distinct charge-state transition (see below).

**Onboarding gate**: when a user pastes an NWC URI, call `getInfo()` and
verify the role-appropriate method is granted:
- Subscriber → must have `pay_invoice`.
- Merchant (self rail) → must have `make_invoice`.
Otherwise reject with a clear UX message; this prevents discovering the
gap mid-billing-cycle.

## Charge state machine (validated in spike)

```
SCHEDULED → INVOICING → AWAITING_PAYMENT → PAID ─┬─▶ (end, self rail)
                ↓             ↓                  │
         FAILED_INVOICE   FAILED_PAYMENT         └─▶ PAYOUT_PENDING ─┬─▶ PAYOUT_COMPLETE
                                                                    └─▶ FAILED_PAYOUT
```

`FAILED_PAYMENT` on a recurring charge flips the subscription to `past_due`
and the retry policy takes over (out of scope for the spike).

`PAYOUT_PENDING` can stall — Wapu's `fiat_transfer` is asynchronous and
the spec gives no SLA. UI must surface "ARS in transit" rather than
treating the charge as fully complete.

## DB model implications

- `charges` needs a `rail` column (`'self' | 'wapupay'`).
- For self rail: store `payment_hash` (idempotency on retry).
- For wapupay rail: store `wapu_deposit_tx_id` (poll target) and, after
  payout, `wapu_payout_tx_id`.
- Worker polling: two independent loops, one per pending stage. Self rail
  doesn't need polling — preimage is sync confirmation.

## Unknowns we accepted

- Spending limits per KYC tier (`/users/spending_limit`) — tier-1 default
  is ~$500. Could bite the demo if the test account is restricted. We'll
  ask Wapu for a tier-2 test account before demo day.
- `make_invoice` quirks across wallet impls (Alby Hub vs Mutiny vs CLN
  NWC). We accepted this risk; a real-wallet pass before submission is
  on the to-do list.
- No webhook means worker latency directly affects subscriber UX. Poll
  interval needs tuning — start at 2s for 30s, then 10s.
